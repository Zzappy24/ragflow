Sandbox d'exécution de code

Yoann Sapienza · Groupe Cyllene

Nos agents IA savent désormais écrire et exécuter du code pour analyser des données : statistiques, requêtes SQL, cartes de contrôle, rapports. Cette note explique pourquoi cette capacité exigeait un environnement d'exécution isolé, comment il est construit, et ce qui a été validé en production.

1. Le besoin : des agents qui calculent au lieu d'estimer

Un modèle de langage seul ne sait pas compter de façon fiable : demandez-lui une moyenne sur 90 000 mesures et il produira une estimation plausible, pas un résultat. La seule réponse rigoureuse est de lui faire écrire un programme qui calcule sur les vraies données, puis d'interpréter le résultat réel. C'est ce que fait notre agent data : il télécharge le fichier du client (via une URL interne à durée de vie courte), exécute une recette d'analyse (Python + SQL DuckDB), et rédige son rapport à partir des chiffres exacts, graphiques compris, affichés directement dans la conversation.

2. Le risque : du code généré par un modèle est du code non fiable

Principe de sécurité : tout code écrit par un modèle doit être traité comme du code potentiellement hostile : défaillant par accident, ou malveillant parce qu'un utilisateur a manipulé le modèle pour le produire (injection de prompt).

Exécuter ce code dans les serveurs de la plateforme serait inacceptable : il y côtoierait les bases de données, le stockage des documents de tous les clients, et les secrets d'infrastructure. Un simple rm -rf, une boucle infinie, ou un script d'exfiltration auraient un rayon d'action maximal.

3. La solution : un bac à sable éphémère par exécution

Chaque exécution de code se déroule dans un Job Kubernetes jetable, créé à la demande dans un espace dédié (rag-sandbox), séparé du reste de la plateforme, et détruit dès la fin de l'exécution. Le code n'a jamais accès à l'environnement qui l'a lancé.

1 · L'agentécrit la recette d'analyse (Python/SQL)
→
2 · Job éphémèrecréé dans l'espace isolé rag-sandbox
→
3 · Exécutionsur les vraies données, ressources plafonnées
→
4 · Résultatchiffres + graphiques renvoyés à l'agent
→
5 · Destructionle bac à sable disparaît sans trace

4. Les couches de défense

CoucheCe qu'elle garantit
Espace dédiéLes Jobs vivent dans rag-sandbox, un namespace séparé des applications, des bases et des secrets de la plateforme.
Droits minimauxLe seul droit accordé au lanceur : créer et suivre des Jobs dans cet espace, rien d'autre, nulle part ailleurs. Le code exécuté, lui, n'a aucun droit sur le cluster.
Réseau verrouilléPolitique « tout est interdit par défaut » : le bac à sable ne joint que ce qui lui est explicitement autorisé : aujourd'hui le stockage de fichiers interne et la résolution de noms. Pas d'internet, aucun accès aux bases ni aux services de la plateforme. Quand un cas d'usage exige l'accès à une base de données (analyses sur données vivantes), il s'ouvre cible par cible : la base concernée uniquement, via un compte en lecture seule restreint au schéma utile, avec des identifiants injectés à l'exécution, jamais visibles du modèle.
Ressources plafonnéesQuota global sur l'espace (nombre de pods, CPU, mémoire) : une boucle infinie ou une bombe mémoire s'étouffe dans son bac à sable sans affecter la plateforme.
Aucun secret embarquéL'environnement d'exécution ne contient ni identifiant, ni clé, ni configuration d'infrastructure. La donnée à analyser arrive par une URL signée à durée de vie courte, valable pour ce fichier uniquement.
Image figéeL'environnement Python (bibliothèques d'analyse, recettes métier) est une image versionnée et auditée : le code ne peut pas installer d'outils supplémentaires.

Conséquence : si le modèle génère un script destructeur (ou si quelqu'un le lui fait générer), le rayon d'action se limite au bac à sable éphémère, qui est détruit de toute façon quelques secondes plus tard.

5. Validé en production

Le dispositif a été éprouvé de bout en bout sur un cas réel (analyse qualité process pour FAMAT, usinage aéronautique) : 90 000 mesures machine analysées par trois recettes (dérive SPC, backtest d'alertes, corrélation température), ~25 à 30 secondes par analyse, cartes de contrôle générées et affichées dans la conversation, résultats identiques d'un run à l'autre. L'agent gère aussi les questions libres (SQL agrégé à la volée) et la vulgarisation des résultats pour un lecteur non technique.

6. Limites connues et prochaines étapes

  • Accès stockage à resserrer : le bac à sable peut aujourd'hui joindre le service de stockage entier ; un accès par bucket est prévu avant d'ouvrir la capacité à des usages moins encadrés.
  • Résolution de noms ouverte : nécessaire au fonctionnement, elle laisse un canal d'exfiltration théorique (tunnel DNS), connu, documenté, à traiter dans une passe de durcissement.
  • Analyses sur bases de données : prochaine étape planifiée : connexion directe du bac à sable à une base cliente (egress ciblé + compte lecture seule + identifiants injectés par l'outil), pour des analyses sur données vivantes sans passer par des exports de fichiers.
  • Généralisation : le même socle servira à tout agent nécessitant du calcul : analyse de fichiers clients, rapports périodiques, contrôles de cohérence de données.
